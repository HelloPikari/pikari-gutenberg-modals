# Session 2 — Triggers stop being a wrapper

## Where this started

Steve opened with a question about template parts and one large omission: no trigger
could choose a modal template. Both turned out to be symptoms of the same thing.

## Decisions, and why

**Settings cannot live on a template part.** `PluginDocumentSettingPanel` does render in
the Site Editor for template parts, so the UI half is possible. The storage half is not:
`WP_REST_Templates_Controller` exposes no `meta` field, so post meta does not round-trip.
But the reason that settled it is a design one, not an implementation one — **settings
stored as block markup travel with the part; REST fields and meta do not**. A theme
shipping `parts/modal-sidebar.html` can only say "I am a sidebar" if placement is in the
markup. That is why core put zero settings on the navigation overlay part and shipped a
Close *block* instead.

**The "missing" template-part selector already existed.** It was wired into all four
trigger surfaces and hidden behind `hasMultiple: parts.length >= 2`. One part means no
selector renders anywhere, and there was no way to create a second. The gap was
discoverability, not code.

**Triggers became a block property.** The Modal Trigger block had two stable states and
neither worked: with styling supports it duplicates Group; without them the Query Loop
card pattern dies, which is exactly the regression Steve hit. A wrapperless variant was
tested and works — `render.php` targets "the first tag", so it decorated the child Group
and kept its styling with zero PHP changes — but it was rejected for silently making only
the *first* child clickable. So: `pikariModalAction` on `core/group` and `core/button`.

**Block variations are discovery, not isolation.** Steve asked whether variations would
insulate us from core changes. They would not — a variation *is* the core block, cannot
add attributes, and is never serialized, so `render_block` must key on the attribute
regardless. Adopted anyway, for the inserter entry, which was the one real cost of the
extension model.

**core/image excluded.** Core's lightbox was renamed ("Enlarge on click"), not removed —
which is why Steve could not find it. The decisive reason is not duplication though: core
attaches a competing click handler to that block via `render_block_core/image`, and it is
on by default.

## What surprised us

**The plan under-specified seven times, and implementers caught most of it.** A load-bearing
gap where `pikariModalPrimaryLinkId` and `pikariModalInlineAnchor` had no writer, so the
flagship card pattern would have shipped unconfigurable. Two build-breakers in Task 6's file
list. A grep gate demanding zero hits for "modal-trigger" that returns 66, because the inline
RichText format is *itself* named that. A brief contradicting itself on variation names.

**Reviews that verify beat reviews that read.** The reviewer that loaded a real
`WP_HTML_Tag_Processor` found that a fix for one finding had introduced a Critical: an
unfiltered `next_tag()` matches `core/button`'s wrapper `<div>`, so every button trigger's
decoration landed on a non-focusable element and focus restore broke. Reasoning about that
diff would not have caught it.

**Per-task review cannot see drift.** Eight tasks passed their own reviews clean. The
whole-branch review then found five open-mode decoration paths, built in different tasks,
disagreeing on `id`, keydown and `aria-expanded` — two of them Level A failures.

**Verification that never ran.** Three times a check appeared to pass without executing:
`tail -3` hid a phpcs failure; `npm run lint:md` does not exist and its "Missing script"
error read as zero violations; a shell loop over multi-word commands returned 127 for four
linters. The pattern was mine, not the subagents'.

## The one I got wrong and had to reverse

I dismissed a reviewer's phpcs `LongNotCapital` finding as a false positive, having tested
`phpcs --standard=phpcs.xml` when `composer lint` runs bare `phpcs`, against a stale vendor.
On a fresh `composer install` from `composer.lock` — what CI does — it fails. Caught only
because the merge ran in a clean worktree. The reviewer was right.

## Open questions

- Does the **Modal Button variation** actually appear in the inserter? `core/button`
  declares `"parent": ["core/buttons"]`, which may confine it and undercut the discovery
  rationale that justified variations at all.
- The **URL mode control is now a bare `TextControl`** where the deleted block used
  `LinkControl` with post search. A real UX downgrade, deliberately not fixed.
- Nothing in the editor has been **seen**. Every editor claim rests on bundle inspection
  and static reasoning, because the editor needs a login.
