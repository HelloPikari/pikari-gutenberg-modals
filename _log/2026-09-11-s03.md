# Session 3 — a plan executed, and a limitation that wasn't real

## Where this started

Steve asked what was next and whether we were ready for another QA round. The answer
turned out to be neither: three fixes had to land first, and the QA round I said I
couldn't do, I could.

## The decisions worth keeping

**Hold the release for #444 rather than ship what was on main.** Two breaking changes
were already stacked up, and #444 carried a third — the `modal-dialog` → `modal-overlay`
rename. Shipping twice would have made CCLF and WinSuccession migrate twice. One
breaking release, 2.0.0, was the cheaper story to tell.

**The plan is an argument, not an authority.** Eleven tasks were executed by separate
implementers with a review after each, and the reviews caught five defects the plan
would have shipped. The most expensive would have been silent: patterns registered on
`init` at priority 10, from a constructor that itself runs during `init` priority 10 —
WordPress never runs callbacks appended to the priority already executing. The plan's
own verification step masked it by firing `init` a second time. Fixed at priority 11 and
pinned by a test proved red at 10.

**A Critical the plan explicitly denied.** Task 8's brief states "editing the default
works". It doesn't: `selectedPart` was resolved by matching the stored `''` against the
synthetic default part's real slug, `modal`, so on the ordinary site whose only template
_is_ the default, both the Edit button and the preview were permanently invisible. The
brief's sentence conflated the record existing with the lookup finding it. I put it to a
reviewer with evidence rather than acting on my own reading, and it came back Critical.

**Rulings, recorded as I went.** Fourteen of them. The ones that changed the work:
extending `EditorIntegrationTest.php` rather than creating it as the plan said, which
would have destroyed the #439 coverage added the same day; dropping a plan test that
asserted behaviour #439 deliberately changed; pinning the editor config to exactly nine
keys with a count assertion, because the plan's stale array would have silently dropped
`triggerBlocks` and `panelWidths`; and excluding `_log/` from the rename, which would
otherwise have rewritten a roadmap line into "modal-overlay → modal-overlay rename".

**Detected Link over Custom URL on Kindler's Keynotes page.** Both would have opened the
right video. Only Detected Link wires the inline "Watch the speaker reel" link itself to
open the modal — with Custom URL, clicking the link would have navigated to YouTube while
clicking the card opened the modal. Verified after: clicking it stays on the page.

## What surprised us

**The limitation I kept repeating was never true.** I deferred an entire QA round on the
grounds that the editor "needs a login I cannot do". Steve pointed out he'd told me the
credentials. wp-env logs in as `admin`/`password`; ten of fourteen QA steps were verified
within minutes, including the two the whole-branch review had named as gating the merge.
The claim originated in todo #459 and I had carried it across sessions without once
re-testing it. It is now corrected in that todo, in the roadmap conventions, and in
project memory.

**Per-task review cannot see what the whole branch does.** Every task passed its own
review. The whole-branch review then found that any Editor-role user was being shown
Create and Edit buttons that dead-end in a raw WordPress 403 — newly reachable precisely
_because_ this branch removed the `hasMultiple` gate that used to hide the panel on
single-template sites. Probed live before fixing: an Editor can read template parts
(`edit_posts`) but not create them (`edit_theme_options`).

**A documented feature that has never worked.** Chasing the inline-format popover, I
found Cmd/Ctrl+M does nothing. `RichTextToolbarButton`'s `shortcutType`/`shortcutCharacter`
only draw the tooltip hint; binding a key needs `RichTextShortcut`, which appears nowhere
in `src/`. `git log -L` dates the lines to the initial commit. CLAUDE.md has advertised it
since v0.0.1. Todo #472.

**Kindler's damage was a third of what the first count said.** A naive grep returned nine
posts; five were revisions and the pattern double-counted closing block comments. Two live
pages, one trigger each. But the two were different shapes — a Button on Home, a Cover on
Keynotes — and `core/cover` is not a trigger block, so only the by-hand route would have
caught it. A migration script would have mangled the second one.

## Dead ends and things not done

- Automation cannot open the inline-format popover by keyboard, because a synthetic text
  selection does not fire the RichText shortcut — which is itself downstream of the
  shortcut never having been bound. The toolbar route (More → Modal Trigger) works, and
  that is how steps 8 and 9 were finally verified.
- The panel's prominent "no templates yet" empty state is unreachable: the plugin always
  provides a synthetic default part, so `parts` is never empty on either theme type. Kept
  anyway, for fidelity to the spec's two-state design, and documented as a gotcha so
  nobody tests for a state that cannot occur.
- Four QA steps still need a human (#459). The one that matters is the Site Editor
  inserter — the only thing the rename could break silently, and no test covers it.
- `main` is protected by a ruleset requiring a PR with no bypass, so the 19 local commits
  could not be pushed directly; they went up as a branch and merged through PR #120 with a
  merge commit, deliberately not squashed, to keep the task-by-task history.
