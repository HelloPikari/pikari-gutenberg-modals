# Session 4 — three bugs, and two of my own claims that were wrong

## Where this started

Steve brought three problems from the Kindler build: a video modal that collapsed around
its video, a global modal that needed a stand-in page, and theme/plugin CSS missing inside
modals. All three were fixed. The more useful output was what the review found afterwards.

## The decisions worth keeping

**Measure before believing anything.** The video bug looked like the iframe was sized
wrong. It wasn't — the iframe measured 1200×675, exactly right, and its _ancestors_ had
collapsed to 169px and were clipping it. Every fix this session started from a measurement
on a real page rather than a reading of the code, and in three separate cases the
measurement contradicted the plausible story.

**Portrait video cannot be auto-detected, so stop trying.** A YouTube Shorts embed URL is
byte-identical to a landscape one. I probed YouTube's oEmbed for a Shorts URL expecting it
to report portrait dimensions; it returns `200×113`. That killed the whole
detect-it-automatically branch and made an author-facing Aspect ratio control the only
honest design — which turned out better anyway, because an explicit ratio works on hosts
the plugin has never heard of.

**Derive width from height, not the other way round.** The fix that actually matters in
fit mode. A 9:16 video at `width: 100%` of a 1200px dialog asks for 2133px of height and
gets clipped by the 90vh cap. `width: min(90vw, calc(var(--modal-video-max-height) *
ratio))` is what makes portrait work at all.

**Simulate the frontend lifecycle rather than move the endpoint.** The missing-CSS bug has
a more fundamental fix — render modal content through a real front-end request via
`template_redirect`, so the lifecycle happens naturally instead of being faked. Rejected:
the REST endpoint's JSON schema, `OPTIONS` discovery and the
`pikari_gutenberg_modals_content_response` filter are a public contract on a shipped 2.x
plugin, and the frontend would have to switch from JSON to an HTML fragment. The tripwire
worth recording: the simulation has already needed two pieces of surgery on shared
infrastructure (unhooking a core `wp_footer` callback, a static flag on our own
`BlockSupport`). **If it needs a third, that is the signal to move to a real request rather
than patch again.**

**Don't extract the trigger decoration yet.** Two of four reviewers wanted the three
near-identical handler bodies factored. The third argued specifically against it, and I
sided with that: extraction touches three _shipped_ handlers days before a release, and the
duplicated thing is an a11y attribute set this plugin has already shipped a mouse-only
trigger bug on once. Per-branch render tests are the mitigation already in place. Deferred,
not dismissed.

**No version bump on the branch.** History does it as its own `chore: release` commit at
tag time, and the peer session's updater PR is outstanding too — guessing the final number
from a feature branch would be wrong.

## What surprised us

**Two things I had documented were false, and my own measurements disproved both.** I
recorded that removing `wp_maybe_inline_styles` recovered "1768 bytes of CSS". It recovered
three URLs and zero bytes — core leaves `extra['path']` intact and unshifts the inlined text
into `extra['after']`, and the collector reads both, so the CSS always arrived, twice. The
byte difference had a different cause entirely and I had attributed one effect to the wrong
mechanism. Separately I wrote that WordPress "registers `block-style-variation-styles`
during `wp_enqueue_scripts`" — it doesn't; core _enqueues_ it there before it exists,
`WP_Dependencies` parks it in `queued_before_register`, and `do_blocks()` registers it and
promotes it. Both halves are needed, which is also the real reason the queue snapshot has to
sit between them. Neither error changed the code; both would have misled whoever read the
comments next.

**A performance recommendation that didn't survive measurement.** The efficiency review
identified `wp_get_global_stylesheet()` as ~25ms of pure waste inside the simulated header,
with a clean argument that its handle is enqueued before the snapshot and can never reach
the response. Unhooking it measured **52.6ms vs 52.2ms with a byte-identical response
hash**. Rejected. The argument was sound and the number wasn't there.

**The branch name nearly cost a minor version.** I started on `fix/video-embed-sizing` and
put a `feat:` commit on it. The autolabeler reads the branch name, so Release Drafter would
have resolved **2.0.1** instead of 2.1.0. Renamed before pushing; the PR came back labelled
`feature`, which confirms it.

**The ETag would have hidden the whole CSS fix.** It hashed only the post, but this
endpoint's output changed shape without any post changing. Every browser holding a 2.0.0
response would have revalidated, been told 304, and served content with the missing styles
indefinitely. Caught in review, not by me. `bump-version.js` is now load-bearing beyond
`release.yml`'s build guard.

**A theory I liked, disproven in one test.** WPForms stores the editor `clientId` as a block
attribute, which looked like an obvious cause of its preview crash. Stripping it changed
nothing — `a.clientId` is the live React prop. The actual cause is that WPForms reads
`wp.data.select('core/block-editor')` from the _default_ registry while `BlockPreview`
renders in an isolated one. Confirmed not-ours by reproducing the identical crash in core's
own Site Editor with our panel out of the picture.

**Cross-session review works, in both directions.** The peer session and I each caught a
factual error in the other's account of the release architecture, by checking rather than
accepting — and by different routes. Claim 2 (CCLF's caret pin) ended up with three
independent confirmations because neither of us took the other's word. Both of us would have
stopped at a plausible-but-wrong answer alone.

## Dead ends and things not done

- Unhooking `wp_enqueue_global_styles` (measured as noise, above).
- The stale-`clientId` theory for the WPForms crash (above).
- A mid-session "cache" that looked like a server-side layer on Kindler turned out to be
  ddev mutagen sync lag — `rsync && curl` in one command reads the container before the file
  lands. Cost two wrong conclusions before I checked the file inside the container.
- `/wrap` deliberately ran after the PR was opened, so the log and roadmap land on the same
  branch rather than trailing behind it.
